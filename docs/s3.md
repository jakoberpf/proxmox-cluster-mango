# Ceph S3 service

Status: live since 2026-08-18. All four phases applied: Reef repository,
radosgw 18.2.4-pve3, pool topology (four bootstrap pools merged to 8 PGs each,
plus 4+2 EC bucket-data pool), and the TLS daemon with a Let's Encrypt
wildcard certificate. Consumers, buckets, and policies are not yet configured.

## Service contract

- Endpoint: `https://s3.mango.cloudsium.de:7480`
- Virtual-host buckets: `https://<bucket>.s3.mango.cloudsium.de:7480`
- Listener: `192.168.8.56:7480`
- Access: LAN and NetBird. NetBird already routes `192.168.8.0/21`.
- Zone: existing single-cluster `default` zone and zonegroup; no realm.
- Daemon: `ceph-radosgw@rgw.mango.service` using `client.rgw.mango`.
- Data: 4+2 EC. Metadata, index, and multipart spill data: replicated size 3/min-size 2.

The endpoint serves a publicly trusted Let's Encrypt certificate issued through
the Cloudflare DNS-01 challenge. The certificate covers `s3.mango.cloudsium.de`
and `*.s3.mango.cloudsium.de`, so clients need no custom CA. certbot on mango
renews it via `certbot.timer`; a deploy hook assembles the RGW PEM and restarts
the gateway.

## DNS contract

Neither required DNS name currently exists. `cloudsium.de` is a registered
domain, so the records can be published in its public DNS (RFC1918 answers) or
served as local overrides by the future Pi-hole stack. LAN and NetBird clients
must resolve the base name and wildcard to mango:

```text
s3.mango.cloudsium.de    A    192.168.8.56
*.s3.mango.cloudsium.de  A    192.168.8.56
```

A dnsmasq-style equivalent is:

```text
address=/s3.mango.cloudsium.de/192.168.8.56
```

Do not reuse the PVE certificate for RGW. The PVE UI has its own Let's Encrypt
certificate for `mango.cloudsium.de` (PVE-managed ACME, auto-renewed); RGW uses
its separate certbot-issued certificate for the S3 names.

## Storage layout and PG budget

Four existing RGW pools have 32 PGs each despite containing only bootstrap
metadata. The rollout exports them, disables autoscaling for RGW pools, and
merges them to 8 PGs one at a time. It waits for every PG to become clean after
each merge. No pool or disk is deleted or reformatted.

The rollout then creates:

| Pool | Type | Durability | Initial PGs |
| --- | --- | --- | ---: |
| `default.rgw.buckets.index` | replicated | size 3, min-size 2 | 8 |
| `default.rgw.buckets.non-ec` | replicated | size 3, min-size 2 | 8 |
| `default.rgw.buckets.data` | erasure coded | 4+2, min-size 5 | 8 |

The estimated result is approximately 240 PG replicas per OSD, below the
current warning threshold of 250. PG counts are deliberately fixed initially;
capacity and object-count growth must be reviewed before increasing them.

## Gated phases

Run the readiness audit at any time:

```sh
make rgw-audit
```

Preview one phase at a time:

```sh
make rgw-plan PHASE=repository
make rgw-plan PHASE=package
make rgw-plan PHASE=pools
make rgw-plan PHASE=daemon
```

There is intentionally no `make rgw-apply`. After review, each phase is applied
directly with its matching confirmation token, followed by `make audit` and
`make rgw-audit` before proceeding to the next phase.

From `ansible/`, the exact form is:

```sh
ansible-playbook plays/ceph_rgw.yml --diff --limit mango \
  -e mango_rgw_phase=repository \
  -e mango_rgw_confirm=mango-rgw-repository
```

Replace `repository` in both extra variables with the reviewed phase name. Do
not run phases together or continue while Ceph has any unclean PGs.

The phases are:

1. `repository`: add the official Proxmox Ceph Reef no-subscription source and refresh APT metadata.
2. `package`: simulate and install exactly `radosgw=18.2.4-pve3`; refuse upgrades or removals.
3. `pools`: export bootstrap metadata, merge RGW PGs, and create the controlled bucket pools.
4. `daemon`: validate DNS/TLS, create the scoped CephX identity, configure Beast, and start RGW.

TLS issuance requires the scoped Cloudflare API token (Zone DNS Write and Zone
Read on cloudsium.de only, managed by Terraform in the cloudflare provider
repository) encrypted in `ansible/group_vars/all/vault.yaml` as:

```yaml
vault_mango_rgw_cloudflare_api_token: <scoped cloudsium.de token>
```

Never print this value or place it in unencrypted variables.

## Consumer isolation

Create a separate non-admin RGW user and bucket policy per consumer. Credentials
belong in Vault or the consuming stack's secret store, never in this repository.
The initial allocation registry is `inventory/s3-consumers.yaml`.
Keep bucket names free of dots so they remain covered by the single-label
`*.s3.mango.cloudsium.de` wildcard certificate.

- Terraform state: one versioned bucket per stack, native `.tflock` locking, and an external state copy.
- GitLab Runner cache: separate disposable bucket with expiry lifecycle rules.
- GitLab backups: versioned backup bucket with retention rules and a copy outside mango.
- Application data: separate bucket and user per application or trust boundary.

User credentials, buckets, policies, lifecycle rules, and a read/write smoke test
are intentionally a later gated phase. They should be prepared only after the
RGW endpoint is running and must not be coupled to daemon activation.

Ceph redundancy is not a backup. All OSDs, the RGW daemon, and its clients share
one physical host failure domain. Important backups and Terraform state require
an independently reachable external copy.

## Terraform backend example

Credentials are supplied through `AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`, not committed backend arguments.

```hcl
terraform {
  backend "s3" {
    bucket                      = "terraform-state-pihole"
    key                         = "production/terraform.tfstate"
    region                      = "us-east-1"
    use_lockfile                = true
    use_path_style              = true
    skip_credentials_validation = true
    skip_region_validation      = true
    skip_requesting_account_id  = true

    endpoints = {
      s3 = "https://s3.mango.cloudsium.de:7480"
    }
  }
}
```

HashiCorp supports non-AWS S3 implementations on a best-effort basis. Test state
locking, interrupted writes, version recovery, and restore procedures before
migrating a production stack.
